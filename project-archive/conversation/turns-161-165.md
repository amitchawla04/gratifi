Every bank gets the same product and nobody gets a fork. I've added this as a new section, "One product, many banks", in the architecture doc, with a drawing.

**Same code for every bank.** The engine, the guardrails, the security controls, the UI kit, the system that produces use cases and the model gateway are identical everywhere. That's why a fix or a new feature reaches every bank at once.

**Tailoring goes through four dials**, from things the bank changes itself to things our engineers build:
1. **Settings.** The bank's own team changes these in an admin console, and a second person approves each change: brand, the assistant's name and tone, which areas are switched on, rules and limits, and which model tier they pay for.
2. **Content.** Their cards, terms, benefits, offers and help articles, whether R360 content is on, and their own test questions.
3. **Connections to their systems.** Links to their core banking, card platform, rewards system and sign-in. We build one per system vendor, so the second bank on the same card platform costs far less than the first.
4. **Extensions.** Journeys only that bank wants. We build them on the same UI kit but keep them outside the shared code. When two or more banks want the same one, it moves into the shared product.

Anything a bank asks for that doesn't fit these four becomes a feature request for the shared product, never a separate version for them. We sort every request into a dial when we sign the contract, and the contract says so.

**Bank one and bank two never meet.** Each bank gets its own copy, usually in its own cloud, with its own keys, database, customer memory and logs. No customer data, conversation or learning passes between banks, or back to R360, unless the bank agrees in writing. What they share is what we build centrally: the code, the UI kit, the standard steps for each use case, and the test suites, which are built from made-up data.

**Updates.** Everyone is on one release schedule. Each bank takes a new release only after it passes that bank's own test questions, at a time the bank picks. No bank may fall more than two releases behind, so we never end up maintaining old versions.

The section also covers the five steps to bring a new bank on, and the risks, each with its fix and owner. The biggest risk is a large bank insisting on changes to the shared code. The answer is to build it as an extension now and add it to the product later if others want it.
